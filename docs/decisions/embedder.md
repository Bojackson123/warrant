# Choosing the embedding model

*Status: decided. Superseding it means re-embedding the corpus and re-recording every
fixture downstream.*

## The answer

**`BAAI/bge-base-en-v1.5`, 768 dimensions, revision
`a5beb1e3e68b9ab74eb54cfd186867f64f240e1a`.**

Four candidates were compared on CPU over the 1,014-document control corpus with 42
hand-written questions, retrieval only. It scored **recall@5 = 0.679** — statistically level
with the best candidate, `nomic-embed-text-v1.5` at 0.690, a gap of half a question — while
embedding the corpus in 8–11 minutes against Nomic's 14–17, and answering a query in under
80 ms against Nomic's 109–214. Where two models are not measurably different in quality, the
decision rule written before the run takes the cheaper one. The corpus costs 2.97 MiB of
vectors at float32.

## Why this decision got measured rather than defaulted

Every other component here can be swapped for the cost of the change itself. The embedding
model cannot. Changing it invalidates the stored corpus vectors, the stored query vectors,
and — because retrieved control ids change, and retrieved text is part of the prompt that
gets hashed — every recorded generation downstream of them. There is no partial migration.
An integrity check can detect that the model moved; it cannot repair anything.

So this is the one choice worth spending half a day measuring before making, and the answer
has to come with numbers rather than with a leaderboard screenshot.

---

## The decision rule, written before the numbers

Recorded here above the results because a rule chosen after seeing the table is not a rule.

The question set has 42 questions, so one question is 2.4 points. A gap smaller than the
sample can support must not decide something this expensive.

1. **Anything above 768 dimensions is out.** Retrieval quality flattens above it and every
   dimension is storage paid twice — once in the database and once in committed fixtures.
2. **Primary metric is recall@5.** Recall at 1, 3, 5 and 10 and mrr are all reported.
   Precision is reported for completeness and not used: with one relevant control per
   question, precision@10 cannot exceed 0.1, so it measures the shape of the label set
   rather than the model.
3. **A gap of two questions or more (≥4.8 points) at recall@5 decides it.** Take the better
   model.
4. **Otherwise the candidates are tied and the cheaper one wins**, in this order: corpus
   embedding wall-clock, then dimensionality, then warm single-query latency. A model that
   is not measurably better does not get to be slower or larger.
5. **A candidate that truncates more than 10% of the corpus is recorded as reading a
   different corpus from the others** — its scores are not comparable on equal terms, and
   the truncation is reported alongside them rather than buried.

## What was measured against

**Corpus.** The vendored SP 800-53 Rev 5 catalog, release 5.2.0, pinned by commit and
content hash in [`data/catalog/PINNED.md`](../../data/catalog/PINNED.md). Chunked one
document per control and per enhancement, following the catalog's own structure, so a
document id *is* a control id and recall means exactly "did it find the right control".

| | |
|---|---|
| Controls and enhancements in the catalog | 1,196 |
| Withdrawn, excluded | 182 |
| **Documents embedded** | **1,014** |
| Parameters resolved to slots | 1,600 |
| Chunk length, median / p90 / p99 / max (tokens) | 136 / 348 / 826 / 1,250 |

Withdrawn controls are excluded because nearly all of them are empty shells pointing at the
control that absorbed them; embedding them adds documents that can never be a right answer
but can still be returned instead of one. SP 800-53A assessment objectives and methods, which
this catalog carries inside every control, are also excluded — they restate the control in
assessment voice, roughly tripling the text and pushing most controls past a 512-token
window while adding little vocabulary a question would match on.

Generated by [`tools/bakeoff/prepare_corpus.py`](../../tools/bakeoff/prepare_corpus.py),
standard library only and deterministic: same catalog in, byte-identical corpus out.

**Questions.** 42 hand-written questions across 15 control families, 12 of them targeting a
specific enhancement rather than a base control, and 9 written as near-miss pairs that a
model can only get right by separating a control from its own enhancement — AC-2 against
AC-2(3), AU-6 against AU-6(1), IA-2(1) against IA-2(2), SC-8 against SC-8(1), CM-7 against
CM-7(1), and so on. They are phrased the way somebody would actually ask, not as
restatements of control titles, because a question set that paraphrases titles scores every
candidate at 1.0 and decides nothing. Listed in full at the end of this document; the file
is [`tools/bakeoff/queries.jsonl`](../../tools/bakeoff/queries.jsonl).

**These questions are scaffolding for this decision and nothing else.** No provenance
labelling, no class balance, no admission criterion for unanswerable questions. They are not
an evaluation set and must not later be reused as one.

**Harness.** [`embed-bakeoff`](https://github.com/rashidalmarri/embed-bakeoff) at commit
`bed0b51ca0a38997e191601aa1f6f89a60c3e3d3`, which takes an already-chunked labelled corpus
and ranks models over it with exact search — a dense matrix multiply over the whole corpus,
no approximate index, so nothing but the model differs between candidates. Each candidate
keeps the query and document prefix its own model card specifies, since a single global
prefix would make this a comparison of models against one arbitrary convention. Reproducing
these numbers needs both this repository and that harness commit.

## Results

42 queries over 1,014 documents, CPU, no candidate failed.

| Model | Dims | recall@1 | recall@3 | **recall@5** | recall@10 | mrr | Corpus s | Query ms | MiB (f32) |
|---|---|---|---|---|---|---|---|---|---|
| `nomic-embed-text-v1.5` | 768 | 0.310 | 0.595 | **0.690** | 0.738 | 0.480 | 1030.9 | 109.0 | 2.97 |
| **`bge-base-en-v1.5`** | 768 | 0.405 | 0.512 | **0.679** | 0.774 | 0.519 | 652.8 | 80.0 | 2.97 |
| `bge-small-en-v1.5` | 384 | 0.238 | 0.524 | **0.619** | 0.690 | 0.387 | 149.4 | 26.5 | 1.49 |
| `MiniLM-L6-v2` | 384 | 0.298 | 0.500 | **0.607** | 0.690 | 0.424 | 47.1 | 9.5 | 1.49 |

Precision is in [`results-pinned.json`](../../tools/bakeoff/results-pinned.json) and omitted
here for the reason given in the rule. `Corpus s` is wall-clock to embed all 1,014
documents; `Query ms` is the warm median for a single query, which is the interactive path.

Timings are from the first of two runs and are the noisy column — the second run moved them
by −29% to +97% on the same machine under different load, while the metrics did not move at
all. Treat them as ratios between candidates measured in the same run, never as absolutes.

### Applying the rule

- Nothing exceeds 768 dimensions, so rule 1 eliminates nobody.
- Best recall@5 is Nomic at 0.690. Within 4.8 points of it: **bge-base at 0.679**, a gap of
  1.1 points — less than half a question. `bge-small` (−7.1) and `MiniLM` (−8.3) both fall
  outside and are eliminated by rule 3.
- Nomic and bge-base are therefore tied, and rule 4 takes the cheaper: bge-base embeds the
  corpus in 652.8 s against 1030.9 s and answers in 80.0 ms against 109.0 ms, at the same
  dimensionality. **bge-base-en-v1.5.**

  Rule 4 decides on a noisy quantity, so it is worth checking that it survives the noise:
  in the second run bge-base was 1.83× faster on the corpus and 2.74× faster per query,
  against 1.58× and 1.36× in the first. The margin moves; its direction does not, in either
  run and on both measures. The tiebreak is not resting on one lucky timing.
- Rule 5 fires on MiniLM, below.

## Truncation: which candidates could read the corpus

Small sentence-transformers silently discard whatever runs past their window. A comparison
that never checks this is ranking models on a corpus it has not established they can read.

| Model | Window | Documents truncated | |
|---|---|---|---|
| `MiniLM-L6-v2` | 256 | 186 | **18.3%** |
| `bge-small-en-v1.5` | 512 | 26 | 2.6% |
| `bge-base-en-v1.5` | 512 | 26 | 2.6% |
| `nomic-embed-text-v1.5` | 8,192 | 0 | 0% |

**MiniLM's window is 256, not 512.** Rule 5 fires: it read a materially different corpus
from the others, so its last-place finish conflates model quality with a window less than
half the size. It is eliminated either way, but the number belongs next to its score rather
than behind it.

**Nomic's 8k context bought nothing here.** It was a candidate specifically because whole
controls might exceed a chunk. The longest control in the corpus is 1,250 tokens, so a
512-token window already covers 97.4% of it, and the long-context advantage is worth 1.1
points of recall@5 — inside the noise floor — at 1.6× the embedding cost. The hypothesis was
worth testing; it did not survive the test.

The 2.6% that bge-base does truncate is a real, bounded limitation: 26 of the longest
controls are embedded from their first 512 tokens. That is a constraint the shipped chunker
has to answer with an explicit split rule, not something to leave implicit.

## Storage

At 768 dimensions over 1,014 chunks:

| | float32 | float16 |
|---|---|---|
| Bytes per vector | 3,072 | 1,536 |
| Corpus total | 3,115,008 B (**2.97 MiB**) | 1,557,504 B (**1.49 MiB**) |

**This is roughly a third of the figure carried in earlier planning**, which sized 768
dimensions at about 9.2 MB. That estimate assumed ~3,000 chunks. Chunking on the catalog's
own control and enhancement boundaries produces 1,014, so the arithmetic comes down with it.
The earlier number should not be restated anywhere; 2.97 MiB at float32 is the figure the
ingest pipeline should be checked against, and a large divergence from it means the chunker
changed, not that the estimate was loose.

## Why this one, in a paragraph

bge-base is the only candidate that is simultaneously at the top of the quality table and
affordable. Nomic edges it by half a question and costs 60–80% more to embed and 1.4–2.7×
more per query for a long-context capability this corpus does not exercise. Below them the gap is
real rather than noise: dropping to 384 dimensions costs 6–8 points of recall@5, which is
what the heavier model actually buys — and it buys it for 9–14× MiniLM's embedding time and
7–8× its query latency. That is a genuine trade, not a free lunch, and it is defensible here
only because the corpus is embedded once at ingest and the 80 ms query cost is what a person
waits for. Had the corpus been ten times larger, the same table would have argued the other
way.

Two findings worth recording because they contradict what was assumed going in:

**`bge-small-en-v1.5` did not beat the lightweight baseline.** It was on the list as
"stronger at the same dimensionality", and on this corpus it is not: it trails MiniLM on
recall@1 (0.238 against 0.298) and on mrr (0.387 against 0.424), edging ahead only at k=3
and k=5, and it does that while costing about 3× the embedding time. More pointedly, MiniLM
achieves its numbers while truncating 18.3% of the corpus and bge-small truncates 2.6% —
so the fair comparison is worse for bge-small than the table suggests. General-purpose
benchmark standing did not transfer to this corpus, which is the entire reason the
comparison was run on this corpus.

**Absolute recall is modest and should not be quoted as a quality claim.** recall@5 of 0.679
means roughly a third of these questions do not surface the right control in the top five.
That is a floor: the question set was deliberately built out of near-miss pairs over a
1,014-way choice, with no reranker and no query expansion. It sets a baseline to improve
against, and it says something useful about `k` — recall climbs from 0.679 at k=5 to 0.774
at k=10, so the retrieval path should not assume k=5 is obviously right.

**No reranker was added.** Added now it would be an unmeasured guess that also invalidates
fixtures. These numbers are what makes a reranker a measurable proposal later rather than a
reflex.

## An operational note the runs surfaced

One of these runs happened while the machine had no DNS, and it exposed something that
matters for a system whose selling point is that it works with no network and no
credentials. Cached weights are necessary but not sufficient: `sentence-transformers` still
issues a `HEAD` against the Hub for each optional config file before falling back to the
cache, and with the network merely *broken* rather than absent those requests retry with
backoff — five retries per file, per model, before proceeding.

The weights load fine offline. The failure mode is not "cannot run" but "runs, eventually,
after several minutes of invisible timeouts", which is worse because it looks like slowness
rather than misconfiguration. Setting `HF_HUB_OFFLINE=1` removes it entirely.

The ingest path should set that explicitly rather than rely on the cache being consulted
first, and should treat any model download at run time as an error rather than a fallback —
a first-run download is precisely the thing that breaks the no-network promise.

## Reproducing this

```
python tools/bakeoff/prepare_corpus.py

cd ../embed-bakeoff
uv sync --extra models

uv run embed-bakeoff validate \
  --corpus  ../warrant/tools/bakeoff/corpus.jsonl \
  --queries ../warrant/tools/bakeoff/queries.jsonl

uv run embed-bakeoff run \
  --config  ../warrant/tools/bakeoff/candidates.toml \
  --corpus  ../warrant/tools/bakeoff/corpus.jsonl \
  --queries ../warrant/tools/bakeoff/queries.jsonl \
  --output  ../warrant/tools/bakeoff/results-pinned.json

uv run --extra models python ../warrant/tools/bakeoff/report_lengths.py
```

The candidate file pins every model to a Hub commit, so a later run fetches the same weights
rather than whatever the mutable tag points at by then. Timings vary with the machine and are
kept in a separate block of the results file for exactly that reason; the metrics do not, so
two runs can be compared on `metrics` alone without wall-clock noise defeating the check.

**The check was run.** Both runs are committed: `results.json` resolved the revisions,
`results-pinned.json` ran against them once frozen. Their `metrics` blocks compare equal
object-for-object — same scores, same dimensionality, same resolved revisions, no failures
in either. Their `timings` blocks do not, by as much as a factor of two on the same machine,
which is exactly why the harness keeps the two apart.

```
python -c "import json; a=json.load(open('tools/bakeoff/results.json')); \
b=json.load(open('tools/bakeoff/results-pinned.json')); print(a['metrics']==b['metrics'])"
```

The second run was performed with `HF_HUB_OFFLINE=1`, on a machine that happened to have no
DNS — so it also demonstrates that the pinned models load from cache with no network at all.
